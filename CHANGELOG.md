# Changelog

## 2026-09-22

- Reported directly ("jarvis says speaking even tho the mouth animation is not there and its done generating text"). Root cause found in `marvis_speech_debug.log`: `play("Me.")` blocked for ~195s inside the audio write, and the next sentence ("What do you need?") logged `lead=194.99s` -- it sat queued that whole time. When a Bluetooth link stalls (not a clean disconnect, just stops draining the output buffer) `sd.RawOutputStream.write()` blocks indefinitely; the mouth freezes (no new `set_levels`) and `play()` never reaches its `indicator.stop_speaking()`, so the overlay's `hide()` (guarded to only fire from `thinking`) can't reach idle and the status stays stuck on "Speaking…". The earlier BT recovery only handled writes that *raise*, not writes that *block*. Fixed the write path so it can never block more than `_WRITE_STALL_TIMEOUT` (5s): `_write_with_levels` now polls `stream.write_available` and writes only as much as fits, resetting a stall deadline whenever the buffer drains and returning `_WRITE_ERROR` (-> existing `_reset_audio`/re-point recovery) if nothing frees up within the window, instead of handing a whole frame to a blocking `write()`. Also hardened `_close_stream` against the same hang moving into teardown: it now takes `drain` -- a clean end of reply drains (`stop()`, so the tail isn't clipped) while interrupts and stalled/dead devices abort (`abort()`, since draining a device that isn't playing would hang), and stop/abort/close exceptions are swallowed so a vanished device can't be left cached as the live stream or derail `play()`'s finally before it resets the indicator (which was a second way the "Speaking" label could strand). `_reset_audio` likewise aborts rather than drains. Verified deterministically with a fake stream: healthy write -> ok, transient backpressure -> ok (no false timeout), permanent stall -> error within the timeout (no hang), interrupt -> interrupt; 77 tests pass. Could not exercise real playback here -- opening an output stream hangs in the headless sandbox (no audio backend) -- so live confirmation on the earbuds is still needed.
- Reported directly ("marvis causes issues with bt earbuds, they sometimes even disconnect and marvis' reply dies when that happens"). Root cause was the then-uncommitted `tts.py` keepalive: a `_keepalive_worker` thread streamed silence to a permanently-open output stream 24/7 whenever Marvis wasn't speaking, added to kill the BT power-save gap (earbuds sleep the A2DP link when idle and clip the next reply's first ~200ms). Holding the link fully active around the clock is the abnormal usage that stresses the earbuds into dropping -- compounded by the A2DP<->HFP profile churn every time the mic opens for STT while the keepalive is mid-write. Second, independent bug: when the device did drop mid-playback, `stream.write()` threw, `_write_with_levels` swallowed it as an interrupt, and `play()` aborted -- with no reconnect, the rest of the reply was lost, and the next sentence's `_get_stream()` (reopening on PortAudio's stale/dead cached default) could throw straight out of `play()`, killing `_speech_worker` and leaking a `_prepare_gate` permit. Fixed both: (1) the keepalive is now device-gated and time-bounded -- new `TTS_KEEPALIVE_DEVICE` (case-insensitive output-device-name substring, empty=off) and `TTS_KEEPALIVE_SECONDS` (default 10) config; `_keepalive_wanted()` streams silence only while the configured device is the active output and only within the window after a reply, then releases the device so the earbuds idle normally. A new `_reply_active` event gates the worker off across a whole reply so it never closes the shared stream between sentences (preserving the committed between-sentence gap fix). Marcelo confirmed via probe that PortAudio (`sounddevice` 0.5.6) exposes device names and that `sd._terminate()`/`sd._initialize()` refreshes the device list in ~33ms. (2) `play()` now recovers from a mid-reply device drop: `_write_with_levels` returns `_WRITE_OK`/`_WRITE_INTERRUPT`/`_WRITE_ERROR`, and on `_WRITE_ERROR` (or a failed reopen) `play()` calls the new `_reset_audio()` (re-enumerates PortAudio so the dead default falls back to the current Windows default) and retries up to `_MAX_RECOVERY_ATTEMPTS` (3), so the reply keeps playing on the fallback device instead of dying. `_speech_worker` now wraps `play()` in try/finally so a playback exception can never kill the worker or leak the pipeline permit. Defaults ship with `TTS_KEEPALIVE_DEVICE` empty (keepalive fully off -> zero earbud stress) until Marcelo sets his earbuds' name; the disconnect-recovery fix is always on. `_reset_audio` is only ever called during playback, when the mic is closed (sequential turn loop), since terminating PortAudio with an input stream open would break recording. All 77 tests pass; gating + reset verified live against the current Yealink default.

- Along the way, misdiagnosed a red herring: seeing two `pythonw.exe main.py` processes at once looked like a duplicate manual launch, but it's normal -- the venv's `pythonw.exe` is a launcher stub that spawns the real interpreter as a child with an identical command line (same thing `jarvis/single_instance.py`'s `kill_other_instances()` already accounts for by excluding a process's own ancestors). No actual duplicate-launch bug existed.

## 2026-09-17 (2)

- Push-to-talk kept dying again even after the `GetAsyncKeyState` fix below, confirmed happening 3 times post-fix. Different root cause this time: `jarvis/assistant.py`'s reply-streaming loop and `jarvis/tts.py`'s `play()` both wait on a queue with a timeout but only checked `interrupt_event` *after* an item actually arrived -- so if the `claude` CLI subprocess (`jarvis/llm.py`) or the edge-tts network stream stalled completely with zero output (a true hang, not an error -- nothing showed up in `jarvis_error.log` for any of the 3 incidents, consistent with this), the main thread sat forever in the `queue.Empty`/blocking-`get()` branch, never reached the interrupt check, never returned from `_run_turn`, and the outer loop in `run()` never got back to polling the push-to-talk key -- so the key looked completely dead (suppressed by the hook, but nothing left to act on it). Fixed by checking `interrupt_event` in the `queue.Empty` branch of the streaming loop (breaks the turn instead of looping forever) and switching `play()`'s blocking `prepared.chunks.get()` to a `get(timeout=0.1)` loop so it re-checks the flag even when no audio is arriving. The stuck `claude` subprocess or TTS fetch thread itself isn't killed -- it's a daemon thread/background process that's simply abandoned and left to finish or die on its own -- but the push-to-talk key is unblocked and the app becomes responsive again immediately.

## 2026-09-17

- Push-to-talk (backtick) would randomly stop responding until Jarvis was restarted (see `WIP.md`'s prior "unconfirmed working theory"). Confirmed root cause: `jarvis/assistant.py` and `jarvis/audio.py` detected the key via the `keyboard` library's `is_pressed()`/`hook_key()`, both backed by a single global Windows low-level keyboard hook that `keyboard` installs exactly once at import and never reinstalls. That hook's callback needs the GIL to run in Python; if heavy work (Whisper transcription, LLM streaming) stalls the GIL past Windows' hook timeout, Windows silently drops the hook with no error and no recovery path in the library. Replaced the detection path with direct `GetAsyncKeyState` polling (`jarvis/audio.py`'s new `is_key_down`/`to_vk_code`), which queries physical key state synchronously with no hook involved, for both the record-start wait and the mid-speech interrupt watchdog. Kept `keyboard.hook_key(..., suppress=True)` only for suppressing the key from leaking into other apps -- if that ever silently drops under load, the worst case is now a stray backtick keystroke, not a dead push-to-talk button. Also found and fixed a related bug surfaced while building this: `to_vk_code` initially resolved a key name to a virtual-key code via `keyboard.key_to_scan_codes(key)[0]`, but that function returns multiple candidate scan codes for punctuation keys and picking index 0 isn't guaranteed to be the right one -- on this machine's layout it resolved "`" to semicolon's code instead of backtick's. Fixed by using `VkKeyScanW` (layout-aware, queries Windows directly) for single-character keys, falling back to the scan-code table only for named keys like "tab".

- The `edge` TTS engine would occasionally speak an all-English reply in the Spanish voice/accent. `jarvis/tts.py` picked the per-reply voice via the module-level `langid.classify()`, whose returned score is an unnormalized, unbounded value (not a 0-1 probability), so `_resolve_edge_voice` was treating any "es" guess as certain even when it was barely ahead of "en" -- and `langid` is unreliable on the short sentences Jarvis often opens with. Switched to constructing a `LanguageIdentifier` directly with `norm_probs=True`, which gives a real 0-1 confidence, and only switch to the Spanish voice when that confidence clears a new `spanish_confidence_threshold` config value (`SPANISH_CONFIDENCE_THRESHOLD` env var, default 0.9), defaulting to English otherwise.
